# 接口探针 Skill

## 目标
将接口定义或真实响应，整理成**给人评审与确认的 Markdown 报告（Human Doc）**，输出内容包括：
- 接口基础信息与参数表
- 响应结构与断言字段清单
- 测试点清单
- 测试场景（正常 / 参数边界 / 鉴权 / 数据逻辑 / 依赖缺失）
- 待确认问题
- 关联接口缺口与下一步建议

本 Skill 的职责是：**接口定义 / 抓包 -> Human Doc**。

它**不直接生成 pytest 脚本**，也**不直接输出 YAML schema**。若后续需要自动化消费，应继续使用 **“用例结构化”** Skill，将本报告转换为 YAML。

参考样例（结构与深度按此对齐，不要复制业务数据）：
- `AI用例/PO订单统计/接口探针报告_getcard.md`

## 适用输入
- Swagger / OpenAPI / Apifox 链接或导出
- 接口文档（Markdown / 飞书 / PDF）
- 真实抓包（URL + 请求参数 + 响应 JSON）
- 用户直接描述的单个或多个接口
- 会话中已配置的 OAS / Apifox MCP（有则优先读取，读不到的字段标待确认）

一次报告默认覆盖**一个主接口**。关联接口只列入缺口表，等有定义或抓包后再单独出报告或续写。

## 核心原则
1. **先帮助人看清契约，再谈自动化**
2. **文档与抓包冲突时，以真实响应为准**，并在参数/字段说明中标注文档错误；不要静默改掉
3. **不编造未见到的字段、枚举、分页能力和失败码**
4. **必须显式列出待确认问题**：不能把「异常处理」这类模糊预期写成确定结论
5. **聚合/卡片接口不要编造 page/limit/list**；仅当定义或抓包证明是列表接口时才设计分页场景
6. **能从响应推导的业务公式要写成数据逻辑场景**（如比率、差值、环比、trend）
7. **不写死账号、Token、完整 Host 到可执行步骤**；环境信息只作报告上下文
8. **若后续要生成自动化，必须进入 `/结构化`**，不要在本阶段写脚本或 YAML

## 执行步骤
1. 解析接口定义，提取 URL、Method、认证方式、所属模块、参数（query/path/header/body）
2. 若有抓包，用真实响应反推 `data` 结构；若只有文档，使用文档 schema，并标明来源
3. 对照文档与抓包，标出必填/类型/枚举/标注错误
4. 输出断言字段清单：字段路径、类型、断言策略
5. 按正向 / 逆向 / 边界列出测试点；说明中可加：
   - **维度标签**：如【维度：功能】、【维度：安全】
   - **设计方法标签**：如【方法：等价类】、【方法：边界值】、【方法：错误推测】
6. 设计测试场景，用例 ID 保持稳定：
   - `TC-00x` 正常场景（全参数 / 仅必填；列表接口才加分页）
   - `TC-10x` 参数边界（空值 / 缺失 / 类型错误 / 非法枚举 / 超长 / 格式非法）
   - `TC-20x` 鉴权异常（无 Token / 错误 Token / 过期 Token）
   - `TC-30x` 数据逻辑（公式、枚举白名单、日期格式、字段完整性）
   - `TC-40x` 依赖缺失（关联资源不存在；无资源 ID 的接口可省略）
7. 把失败码未知、分页是否存在、过期 Token 如何构造、文档矛盾等写入「待确认问题」
8. 列出关联接口是否已有真实响应
9. 导出 Markdown 报告；结尾提示下一步使用 **“用例结构化”**

## 输出定位
本 Skill 的产物是：
- **Human Doc（给人看的文档）**

不是：
- `test_assets/` 下的 requirements / cases / questions YAML
- pytest / Playwright 脚本
- 可直接执行的 curl / 运行命令

若用户需要后续自动化链路，应明确提示：
- 下一步使用“用例结构化” Skill
- 将当前 Markdown 报告转换为 YAML schema

## 导出方式
生成报告后，建议保存到：

```text
AI用例/<模块名>/接口探针报告_<接口短名>.md
```

示例：`AI用例/PO订单统计/接口探针报告_getcard.md`

## 输出模板

```markdown
# 接口探针报告：<模块名> - <接口短名>

> 生成时间：YYYY-MM-DD
> 接口：<接口中文名> `<path>`
> Method：GET/POST/...
> 响应来源：抓包 / Swagger / 二者对照

## 1. 接口基础信息

| 项目 | 内容 |
|------|------|
| 接口名称 | ... |
| URL | `/path` |
| Method | GET |
| 认证方式 | Bearer Token（header Authorization） |
| 所属模块 | ... |
| 环境备注 | 管理端/客户端（不要把 Token 写入报告） |

## 2. 请求参数定义

| 参数名 | 位置 | 类型 | 必填 | 说明 |
|--------|------|------|------|------|
| `field` | query/path/header/body | string | ✅/❌ | 枚举、格式、文档与抓包差异 |

## 3. 响应结构

> 来源：真实抓包 / 文档 schema
> 示例 URL：`/path?...`（可打码敏感值）
>
> 报告中用 json 代码块贴响应，示意：
> `{ "code": 10000, "message": "操作成功！", "data": {} }`

### 断言字段清单

| 字段路径 | 类型 | 断言策略 |
|----------|------|----------|
| `code` | int | 必须等于 10000（若环境码不同，标待确认） |
| `message` | string | 非空 |
| `data` | object/array | 非 null |
| `data.xxx` | ... | 类型 / 枚举 / 范围 / 格式 |

## 4. 测试点清单

> 本章节按 **正向 / 逆向 / 边界** 输出，供「用例结构化」映射为 requirements。
> 标签格式：`【维度：功能】`、`【方法：边界值】`

| 类型 | 测试点 | 说明 |
|------|--------|------|
| 正向 | 成功响应结构完整 | [说明]【维度：功能】【方法：场景法】 |
| 正向 | 派生字段逻辑一致 | [说明]【维度：功能】【方法：场景法】 |
| 逆向 | 未授权被拒绝 | [说明]【维度：安全】【方法：错误推测】 |
| 边界 | 必填/枚举/格式非法 | [说明]【维度：功能】【方法：边界值】 |

## 5. 测试场景设计

### 5.1 正常场景（Happy Path）

| 用例ID | 场景描述 | 请求参数 | 预期结果 |
|--------|----------|----------|----------|
| TC-001 | 全参数正常调用 | 关键参数列表 | `code=10000`，`data` 结构符合断言清单 |
| TC-002 | 仅必填参数调用 | 只传 required=true；省略可选字段，不要改成传空串 | 成功；可选过滤缺失时的数据范围需说明 |
| TC-003 | 分页（仅列表接口） | `page` / `limit` | 校验 list 结构；非列表接口删除本行 |

### 5.2 参数边界异常

| 用例ID | 场景描述 | 请求参数 | 预期结果 |
|--------|----------|----------|----------|
| TC-101 | 必填空值 | `field=` | 待确认：失败码或空数据，写入问题清单 |
| TC-102 | 必填缺失 | 不传该参数 | 待确认 |
| TC-103 | 格式非法 | 如日期 `2026/01/01` | 待确认 |
| TC-104 | 枚举非法 | 文档外取值 | 待确认 |
| TC-105 | 超长 | 超过合理长度 | 待确认 |

### 5.3 鉴权异常

| 用例ID | 场景描述 | 请求参数 | 预期结果 |
|--------|----------|----------|----------|
| TC-201 | Token 缺失 | 不传 Authorization | 待确认：HTTP 401 或业务失败码 |
| TC-202 | Token 错误 | `Bearer invalid_token` | 待确认 |
| TC-203 | Token 过期 | 过期 Token（构造方式未知则标问题） | 待确认 |

### 5.4 数据逻辑校验

| 用例ID | 场景描述 | 断言逻辑 |
|--------|----------|----------|
| TC-301 | 派生字段公式 | 如 `rate = a / b * 100`（误差阈值写明） |
| TC-302 | 差值/环比一致 | 如 `diff = current - ring` |
| TC-303 | 枚举白名单 | 如 `trend ∈ {up, down, flat}` |
| TC-304 | 格式 | 如日期 `YYYY-MM-DD - YYYY-MM-DD` |

无派生字段时，本节可只保留字段完整性与枚举校验。

### 5.5 依赖缺失（可选）

| 用例ID | 场景描述 | 请求参数 | 预期结果 |
|--------|----------|----------|----------|
| TC-401 | 关联 ID 不存在 | 不存在的 `id` | 待确认 |

## 6. 待确认问题

| 编号 | 问题描述 | 建议确认方式 |
|------|----------|--------------|
| Q1 | 非法/缺失参数时的精确业务码？是否允许成功码但 data 为空/全 0？ | 对照真实响应，列出失败码白名单 |
| Q2 | 鉴权失败是 HTTP 401，还是 HTTP 200 + 业务失败码？ | 抓一次无 Token / 错 Token 响应 |
| Q3 | 文档与抓包冲突的字段以谁为准？ | 与后端确认并回写文档 |

## 7. 后续需要补充的接口

| 接口 | 真实响应是否已提供 |
|------|-------------------|
| 当前主接口 | ✅ / ❌ |
| 关联接口 | ❌ 待提供 |

## 8. 下一步建议

- [ ] 评审参数表、断言清单与场景是否完整
- [ ] 确认「待确认问题」中的开放项，避免把模糊预期结构化成确定 case
- [ ] 如需生成自动化资产，执行 **“用例结构化”** 将本报告转换为 YAML schema
- [ ] 建议模块名：`<module_snake_case>`（只建议，不创建文件）
```

## 输出要求
执行本 Skill 时，输出应包含：
1. 接口契约摘要（路径、方法、认证、关键参数）
2. 参数表与响应断言清单
3. 测试点清单
4. 按 ID 分段的测试场景
5. 待确认问题
6. 关联接口缺口
7. 下一步提示：如需自动化，请进入“用例结构化”

预期结果未知时，必须写成「待确认：…」，并在第 6 节建对应问题，不要写「异常处理」了事。

## 不要做的事
- 不要直接生成 pytest / Playwright / curl 可执行脚本
- 不要在此阶段输出 YAML schema
- 不要编造响应字段、selector、失败码、分页结构
- 不要把未确认预期写成确定结论
- 不要给非列表接口设计 page/limit
- 不要把 Token、密码、完整可调用 Host 当作用例数据写死
- 不要把 Human Doc 当成自动化直接输入
- 不要一次把未提供响应的关联接口写成已覆盖场景

## 成功判定标准
- 报告适合给测试 / 开发共同评审
- 文档与抓包差异被显式标出
- 测试点、场景、待确认问题三层清晰，能被「用例结构化」稳定拆成 requirements / cases / questions
- 用例 ID 分段稳定，后续补接口时不重号
- 明确指向下一步：需要自动化时使用“用例结构化” Skill
